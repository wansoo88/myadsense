# 보고 — 서버 git 작업트리 전환 + CRLF 구조적 차단

## 한 줄 결론
서버를 **깨끗한 git 작업트리로 전환 완료**(백업·런타임 보존 실증, pull 실동작 증명).
다만 **`origin/main` 이 로컬 `main` 보다 2커밋 뒤**여서 `renderer.py` md5 일치(DoD ④)는 **미달** —
**PM 의 `git push` 가 있어야 완료**된다. 나는 push 권한 밖(경계: git commit/push 금지)이라 여기서 멈췄다.

## ⛔ 차단 사유 (가장 먼저 볼 것)

ORDER 의 전제 "repo HEAD `67e934e`" 는 **GitHub(origin/main) 기준으로는 맞지만 로컬 기준으로는 틀렸다.**

| 위치 | HEAD | `renderer.py` md5 |
|---|---|---|
| 로컬 `main` | `c7e836e` (origin 보다 **2커밋 앞**) | **`a5e0d578b27046594b0ce75afdee89d3`** (수정본) |
| `origin/main` (GitHub) | `67e934e` | `142f9c803d965a5fc5ed32af969df7bc` (구버전) |
| 서버 (전환 후) | `67e934e` | `142f9c803d965a5fc5ed32af969df7bc` |

즉 **renderer 수정 커밋 `f2e85fb` 가 아직 GitHub 에 push 되지 않았다.**
서버가 아무리 정상적으로 `git pull` 해도 GitHub 에 없는 코드는 받을 수 없다.

```
$ git rev-list --left-right --count origin/main...main
0	2      ← 로컬이 2커밋 앞
```

### PM 이 해야 할 3단계 (이후 서버는 완전 자동)
```bash

# 2) push (이게 없으면 서버는 영원히 구버전)

# 3) 서버 첫 pull 1회 (이후로는 daily.sh 가 스스로 pull)
```

> 새 `daily.sh` 는 git 으로만 전달해야 하는데(아래 §4 참조), 그 전달을 위한 최초 1회는 사람이 당겨야 한다.

## 1. `.gitattributes` 신설 ✅

`D:\cashflow\pjt12-adsense\.gitattributes` (신규, md5 `b3e638ff6f59911d860e5611a88155d0`, CR 0바이트)

```
* text=auto eol=lf
*.sh *.py *.yaml *.yml *.json *.md  → text eol=lf
*.ps1 → text eol=crlf   (Windows 전용 스크립트만)
```

- 저장소에 바이너리 없음(`.bat/.cmd/이미지` 0건) 확인 후 전역 `* text=auto eol=lf` 적용 — 안전.
- **로컬 작업트리 영향: 없음(잡음 0).** 적용 전후 `git status` 비교 시 신규 `modified` 파일 **0개**.
  이유: 커밋된 blob 은 이미 전부 LF(`CRLF-IN-INDEX` 스캔 결과 0건)라 clean 필터가 CRLF 를 흡수한다.
- 다만 현재 로컬 작업트리에는 **CRLF 파일이 61개** 남아 있다(과거 `core.autocrlf=true` 체크아웃 산물).
  다음 체크아웃/클론부터 LF 로 정리되며, **서버 체크아웃은 이제 무조건 LF** 라 사고 경로는 이미 끊겼다.
- ⚠️ 부수 발견: `grep -c $'\r'` 는 이 환경에서 신뢰할 수 없다(daily.sh 를 "CR 0" 으로 오보).
  본 보고의 모든 CR 수치는 **파이썬 바이트 카운트**(`open(...,'rb').read().count(b'\r')`)로 측정했다.

위치는 ORDER 대로 **selftest 앞**(새 코드로 회귀 테스트가 돌도록).

포함 내용:
1. `GIT_TERMINAL_PROMPT=0` + `timeout 120` — cron 은 TTY 가 없어 git 이 자격증명을 물으면 **영원히 멈춘다**. 이중 차단.
2. 실패 시 **비치명적** + 배너 + **드리프트 목록(`git status`) 출력** + 재현 명령.
3. 성공 시 `head_before → head_after` 와 **반영된 커밋 목록** 로깅.
4. `chmod +x scripts/*.sh` 자가치유 (§2-4).
5. **자기 자신 교체 방지**: pull 이 `daily.sh` 를 바꾸면 새 버전으로 **1회 `exec` 재실행**(`ADSENSE_DAILY_REEXEC` 로 무한루프 차단).
   근거: 서버 실측상 git 이 **같은 inode 에 덮어쓰는 경우가 있고**(inode 294446 유지 관측), 새 `daily.sh` 는
   9,707바이트로 bash 읽기 버퍼(8KB)를 넘는다 → 실행 중 교체 시 엉뚱한 줄을 실행할 실질 위험이 있다.
6. `.git` 없으면 경고만 남기고 스킵(비-git 환경 저하 동작).
7. 최종 `exit` 전파에 `pull_rc` 포함 — selftest 와 동일한 advisory 패턴(막지 않되 조용히 넘어가지도 않음).

## 5. 판단 근거 — 왜 새 `daily.sh` 를 서버에 scp 하지 않았나 (중요)

"일단 scp 로 올려두면 되지 않나"가 **가장 그럴듯한 오답**이라 실험으로 확인했다.

```
서버 작업트리에 로컬 수정이 있으면(= scp), 이후 GitHub 에 같은 파일이 push 되는 순간
error: Your local changes to the following files would be overwritten by merge: daily.sh
Aborting
```
**내용이 바이트 단위로 동일해도 git 은 거부한다**(직접 재현 확인). 즉 scp 로 올리면
**"매일 pull 이 실패하는" 영구 지뢰**를 심는 것 — 이 ORDER 가 없애려는 문제를 오히려 고착시킨다.

그래서 서버 작업트리를 **깨끗한 상태로 유지**했고, 새 `daily.sh` 는 **git 경로로만** 전달되게 남겼다.
(§ 차단 사유의 3단계 명령이 그 전달 절차다.)
